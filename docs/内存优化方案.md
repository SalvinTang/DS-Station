# DS Station 内存优化方案

> 适用版本：`1.1.2` 及以后
> 状态：待实施（本文档只给方案，不含代码改动）
> 关联：`开发记录.md`「技术方案 / 长期约束」

---

## 〇、结论摘要

现状的常驻内存大约 **340–450MB**，其中 2/3 花在「用户看不见」的地方：一个几乎永不显示、
但始终全速运行的 DeepSeek 网页渲染进程，以及两个启动时就建好、几乎永不显示的窗口。

优化分三层，**前两层做完，预期落到 150–220MB**，且不改任何用户可见行为：

| 层 | 内容 | 预期收益 | 风险 | 是否改代码路径 |
|---|---|---|---|---|
| P0 | 清理「无效功」：重复推送、全量轮询、多余窗口、超重前端包 | −100~160MB + 明显降 CPU | 无 | 局部，不改架构 |
| P1 | 页面空闲回收（`about:blank` ↔ 唤醒预热） | −70~140MB（空闲态） | 中，需实测 | 新增一个模块 |
| P2 | 冷启动不再预载页面 | −45~70MB（启动态） | 中高 | 动登录门禁 |

**建议只做 P0 + P1。** P2 留作观察项，等 P1 稳定跑过一个版本再评估。

---

## 一、三条硬约束

方案里任何一条改动，都必须同时满足：

1. **功能不变**
   登录判定、发消息、流式回答、停止/继续生成、历史列表、历史会话、搜索结果、退出登录——
   这八条链路的对外行为必须完全一致。允许的只有「首次多等几百毫秒」，且必须被用户打字时间掩盖。

2. **不阻碍后续开发**
   不允许出现「新增功能时要额外记得做 X」这类隐性知识。因此回收/唤醒的决策必须**收敛到一个模块**，
   业务代码只允许调用一个入口，禁止散落的 `loadURL` / `destroy` / 长持 `DeepSeekPage` 实例。

3. **可回退**
   所有行为改动要有开关（环境变量或隐藏设置），出问题能一键回到当前行为，不需要回滚代码。

## 二、内存到底花在哪（诊断）

页面「隐藏」不等于「省内存」：Chromium 对隐藏窗口只做**降速**（暂停 rAF、压低 timer），
不释放 JS 堆、DOM 和已解析代码。而本项目因为 `index.ts:78-81` 的三个全局 switch +
`main-window.ts:139` 的 `backgroundThrottling: false`，连降速都没有——页面在用户看不见时仍全速跑。

| 组成 | 量级 | 隐藏时是否释放 |
|---|---|---|
| 渲染进程基线（V8 isolate / Blink / Skia） | 45–70MB | ❌ 进程活着就占 |
| DeepSeek SPA 的 JS 堆（React、流式解析、markdown） | 50–120MB | ❌ 只增不减 |
| 会话 DOM（有虚拟列表，但会话越长越胖） | 10–60MB | ❌ |
| GPU 合成层 surface | 20–40MB | ✅ 窗口隐藏时已丢 |
| HTTP 内存缓存（头像、图标） | 5–20MB | 需 `clearCache()` |

**90% 集中在渲染进程的 JS 堆和 DOM 上。** 想省下来，只有两条路：让文档重新加载一次，
或者让进程退出。其余都是零头。

另外：常驻 **5 个渲染进程**。其中 `GuideWindow`（首次/未登录才显示）和 `TrayMenuWindow`
（点托盘才显示）在 `index.ts:221-222` 启动即创建，两个加起来 120–160MB，几乎从不被看到。

## 三、P0：清理无效功（零风险，先做）

这一层不改变任何行为，只是把重复计算、重复传输、重复渲染去掉。

### P0-1 流式推送去重

**现状**：`page-driver.ts:552` 每 150ms 读一次整条回答的 `outerHTML`；
`:564` 的推送条件 `if (current && now - lastPushAt >= 300)` **没有判重**——
回答卡住或思考中时，同一份 HTML 会被反复序列化、反复跨进程传输、反复重渲染。

**改法**：
- 页面侧先比「长度 + 尾部 64 字符指纹」，变了才取 `outerHTML`；
- 推送条件补上 `changed`。

**收益**：静止期 IPC 与序列化直接归零；生成期字符串拷贝减少 ~60%。
**验收**：`DS_CHAT_TEST=1` 下，一次 60 秒回答的推送次数应显著下降，且界面刷新节奏不变。

### P0-2 轮询只读最后一条

**现状**：`waitForAnswerChange`（`page-driver.ts:495`）每 150ms 调 `listAnswers()`，
它把页面上**所有**历史回答都序列化传回主进程（`page-driver.ts:463-475`），
`baseline` 数组还要在整个请求期间（最长 2 分钟）常驻。

**改法**：新增 `lastAnswerText()`，只读最后一条；baseline 从 `string[]` 降为一个字符串。

**收益**：长会话下每轮少搬几 MB；baseline 常驻内存从 MB 级降到 KB 级。
**风险**：`waitForAnswerChange` 原本用「最后一条文本变化」判断，语义不变。
注意 `listAnswers().length` 还被用作 `answerIndex`，那个调用点保留。

### P0-3 `innerText` → `textContent`

**现状**：`selectors.ts:123` 的 `dsText` 首选 `el.innerText`。这个属性会触发 style/layout 重算，
而它在 150ms 轮询循环里被调用。

**改法**：改 `textContent` + 现有正则压空白（`dsText` 已经有这个规整逻辑）。

**收益**：每轮省一次全页布局；CPU 与 layout 对象垃圾一起降。
**风险**：`textContent` 不合并块级换行。回答正文的行内结构（`<p>`、`<li>`）需要确认压空白后
文本仍可用于「变化检测」和「复制」——只做检测用，展示一律走 `html`，所以风险很低。

### P0-4 常驻窗口懒创建

**现状**：`index.ts:221-222` 启动即建 `GuideWindow` 和 `TrayMenuWindow`。

**改法**：首次 `show()` 时创建，实例复用；托盘菜单可在首次点击时创建（那次点击本来就有
`app.focus({steal:true})` 的 100ms 缓冲）。

**收益**：−120~160MB。
**风险**：首次打开多 100–200ms。这是纯感知问题，不是功能问题。

### P0-5 快捷窗口包体瘦身

**现状**：`out/renderer/assets/quick-*.js` = **2.8MB**，来自 `markdown-render.ts:19-20`
全量引入 `highlight.js`（190 种语言）和 `katex`。这个窗口常驻，等于常驻一份解析后的代码。

**改法**：
- `highlight.js/lib/core` + 显式注册 8–10 种常用语言；
- `katex` 改成只在文本里出现 `$`/`$$` 时 `await import()`。

**收益**：−800KB 源码、−10~25MB 渲染堆，启动更快。
**风险**：冷门语言没有高亮（退化成纯文本，不影响功能）；公式首帧多一次异步加载（本地文件，<50ms）。

### P0-6 常驻数据加上限

- `markdown-render.ts:101` 的 HTML 缓存 8MB → 2MB（LRU 已有，改常量）；
- 快捷窗口的 `messagesInner` 与 `historyAllMessages` 无上限，建议限制 DOM 组数（数据保留，
  往上滚动时按需重建，现有 `renderOlderFromMemory` 已经具备这个能力）。

**收益**：消除「连续使用一天后内存只涨不降」的长尾。

## 四、P1：页面空闲回收（核心）

### 4.1 关键判断

「用户打开面板时才创建页面」这个想法方向对，但**单独的延迟创建收益接近 0**——
面板在应用启动时就会自动打开（`startup.ts:63`、`:96`），「用户打开」就是「应用启动」。
真正省内存的是「会话被丢弃后把页面还回去」。

同样，**回收时机不在「关面板」那一刻**：用户关闭面板时，面板仍是 content 态、下次打开还要
接着看上次对话。此时回收，追问会接到错误的会话——这是功能破坏，不是性能取舍。

### 4.2 三个天然回收点

| 时机 | 依据 | 安全性 |
|---|---|---|
| 新对话 | `startNewChatOnPage`（`index.ts:1513`）、空态发送前（`:869`） | 高：旧会话已确定被丢弃 |
| 重置为新聊天 | `applyResetRule`（`quick-window.ts:927`，默认 10 分钟，`settings.ts:72`） | 高：同上 |
| 退出登录 | `handleLogout`（`index.ts:748`） | 高：本来就在清数据 |

补充一个可选的第四点：面板为空态、且隐藏满 10 分钟 → 回收（此时没有会话可丢）。

**注意顺序**：新对话必须**先执行 `startNewChat`，再回收**——开新会话本身要点页面上的按钮。

### 4.3 唤醒时机

在 `QuickWindow.show()` 里启动一个 700ms 的延迟预热，`hide()` 时取消。
用户唤出面板 → 看到输入框 → 打字 → 回车，通常 5–15 秒；页面 `loadURL` + SPA 首屏 2–4 秒，
加载完全被打字时间掩盖。

**这个风险已经被你们无意中验证过了**：已登录启动时，页面就是在「从未显示过的窗口」里
加载成功的（正是 `index.ts:67-81` 那几个 switch 存在的原因）。唤醒加载与首次加载是等价路径。

唯一新变量：同一 webContents 反复 `loadURL` 时 Cloudflare clearance 能否稳定复用。
`index.ts:775`、`:793` 现在就在做 `loadURL`，路径已在用——但仍需观察是否触发验证挑战。

### 4.4 接口设计（保持后续开发顺畅的关键）

新增 `src/main/deepseek/page-keeper.ts`，把「页面在不在」「什么时候加载」「什么时候回收」
全部收进这一个模块：

```ts
type PageState = 'warm' | 'cold' | 'loading'

class PageKeeper {
  get state(): PageState
  /** 保证页面可用（冷态时触发加载并等到 composer 出现），并发调用去重 */
  ensure(timeoutMs?: number): Promise<boolean>
  /** 会话丢弃后调用，导航到 about:blank 释放 SPA 堆 */
  release(reason: 'new-chat' | 'reset' | 'logout' | 'idle'): void
  /** 统一入口：业务代码不再直接 new DeepSeekPage */
  withPage<T>(fn: (page: DeepSeekPage) => Promise<T>): Promise<T | null>
}
```

**为什么必须是 `withPage` 而不是暴露 `page`**：`DeepSeekPage` 在构造函数里存了
`view` 引用（`page-driver.ts:57`）。一旦页面重建，任何被长期持有的实例都会指向死的
webContents，而 `run()` 会把异常吞掉返回 `null`（`:64-72`），表现出来是「操作静默失败」，
排查成本极高。用 `withPage` 从结构上杜绝这类实例泄漏。

### 4.5 必须一并处理的四个点

1. `index.ts:207` 的 `dom-ready`（装 header 捕获钩子）和 `index.ts:213` 的 `before-input-event`
   （⌘H）原本挂在启动时，要挪进 `ensure()`，否则重建后失效。
2. `startup.ts:138` 的 `watchLogin` 长期持有 `DeepSeekPage`，是唯一的长持实例，必须走 `withPage`。
3. `handleHistoryToggle`（`index.ts:1247`）在空态下读页面列表，入口必须先 `ensure()`。
4. 主窗口可见时**不回收**——用户可能正开着主窗口在看 DeepSeek 网页。

### 4.6 收益与验收

- 空闲 15 分钟后，pageView 的 `privateBytes` 从 ~150MB 降到 <60MB（渲染进程基线仍在）；
- 唤醒后首条回答端到端延迟增加 <1s（对比基线）；
- 连续 20 次「新对话 → 追问 → 关面板 → 再唤出」，功能与当前完全一致；
- 连续 20 次唤醒，Cloudflare 无新增验证挑战。

**回退开关**：`DS_PAGE_RELEASE=0` 时 `release()` 直接返回，行为与现状一致。

## 五、明确不做的事（红线）

| 方案 | 为什么不做 |
|---|---|
| CDP `Page.setWebLifecycleState` / `HeapProfiler.collectGarbage` | `page-driver.ts:25` 已写明 CDP 是 Cloudflare 明确盯的机器人特征，P0 验证来之不易 |
| `--renderer-process-limit` | 远程站点与本地 `file://` 在站点隔离下基本合不到一起；真合了则一窗崩溃全连坐 |
| 定时 `reload()` | 丢当前会话与滚动位置，且有重新触发人机验证的风险 |
| 销毁 `WebContentsView` 再重建 | 比 P1 只多省 45–70MB 的进程基线，代价是重写页面生命周期、多一套故障模式。**暂缓**，除非 P1 上线后数据显示仍不够 |

## 六、实施顺序

```
第 1 步  P0-1 / P0-2 / P0-3     半天，纯局部改动，无架构影响
第 2 步  P0-4 / P0-5 / P0-6     一天，独立可并行
第 3 步  加 DS_MEM_TEST 度量      复用现有 DS_*_TEST 自检体系，先拿到基线数据
第 4 步  P1（PageKeeper）        两到三天，含唤醒时序实测与 Cloudflare 观察
第 5 步  观察一个版本 → 决定 P2 是否值得
```

**先做第 3 步的度量，再动 P1。** 现在的数字都是估算，`getProcessMemoryInfo().privateBytes`
能给出真实基线，也能直接判断 P1 是否达到了预期——不要凭感觉优化。

---

## 七、后续开发的接入规矩

写进 `开发记录.md` 的「长期约束」，防止优化被后续迭代悄悄推翻：

1. **禁止**在业务代码里直接 `new DeepSeekPage(win.pageView)`；一律 `pageKeeper.withPage(...)`。
2. **禁止**在 `page-keeper.ts` 之外调用 `loadURL` / `webContents.close()`。
   现有 `index.ts:775`、`:793` 两处要在 P1 时收敛进去。
3. 任何新增「需要页面」的功能，入口第一行就是 `await withPage(...)`，不要假设页面热着。
4. 长时间运行的轮询 / interval，必须能被 `release()` 打断（复用现有 `StreamToken` 或
   在 `PageKeeper` 里维护在飞任务计数）。
5. 新增自检一律走 `process.env.DS_*_TEST` 体系，不要另起一套。

## 附：度量方法

```ts
// 每 30 秒打一次，观察 privateBytes 的变化
const info = await mainWindow.pageView.webContents.getProcessMemoryInfo()
console.log('[内存] page private=', Math.round(info.privateBytes / 1024), 'MB')

for (const m of app.getAppMetrics()) {
  console.log(m.type, m.pid, Math.round(m.memory.workingSetSize / 1024) + 'MB')
}
```

`app.getAppMetrics()` 的 `workingSetSize` 单位是 KB，每个渲染进程一条，
「哪个进程在涨」一眼可见。建议做成 `DS_MEM_TEST=1` 自检项，与现有自检体系保持一致。
